### Explicación y seguimiento por pregunta

1. **B, Duda:** dividir responsabilidades en módulos cohesivos con interfaces claras evita que cambios de reportes afecten lógica de precios. Confirmar distinción cohesión/acoplamiento y principio de responsabilidad única.
2. **A, Seguro:** depender de una abstracción de persistencia e inyectar implementaciones desacopla reglas de negocio de SQL Server y facilita pruebas con dobles.
3. **C, Adivinando:** el diagrama UML de componentes representa componentes, dependencias e interfaces proporcionadas y requeridas. **No consolidado**; enlaza con dificultad previa al elegir diagramas UML.
4. **B, Duda:** un cliente tiene cero o más pedidos; cada pedido una o más partidas; cada partida corresponde a un producto y un producto puede figurar en múltiples partidas. Reforzar lectura de multiplicidades en ambos extremos.
5. **A, Seguro:** separar Cliente(idCliente, nombreCliente) elimina repetición y anomalías de actualización al mantener Factura(idFactura, idCliente, fecha) con clave foránea. Concepto de dependencia transitiva y normalización.
6. **C, Duda:** encapsular algoritmos de transportistas bajo un contrato común favorece sustitución/extensión sin condicionales repetidos; se vincula con patrón Strategy y principio abierto/cerrado. Reforzar frente a patrones similares.
7. **B, Adivinando:** incrustar partidas pequeñas, no compartidas y generalmente leídas junto con el pedido facilita consultas agregadas y operaciones atómicas a nivel de documento, según soporte del motor. **No consolidado**.
8. **A, Adivinando:** fragmentar horizontalmente clientes por país permite mantener cada subconjunto en su región y consultar principalmente datos locales. La vertical separa columnas; replicar globalmente violaría la restricción dada. **No consolidado**.
9. **C, Seguro:** versionar el contrato API y mantener adaptadores de compatibilidad permite migraciones graduales sin romper a consumidores no actualizables inmediatamente.
10. **B, Adivinando:** realizar la comprobación y creación del préstamo de forma atómica/autoritativa evita dos préstamos activos; debe reforzarse con una restricción de unicidad o mecanismo de concurrencia apropiado. El catálogo tolera replicación asíncrona. **No consolidado**; se relaciona con CQRS y consistencia.

### Lógica SQL de NULL — prioridad nueva crítica

- SQL utiliza lógica de **tres valores**: TRUE, FALSE y UNKNOWN. En cláusulas `WHERE` solo pasan filas cuyo predicado vale TRUE.
- `x = NULL` y `x <> NULL` normalmente evalúan UNKNOWN: para comprobar ausencia se usa `IS NULL` y presencia `IS NOT NULL`.
- En la pregunta 5, `region <> 'Norte'` devuelve TRUE solo para `'Sur'`; NULL no se considera distinto a `'Norte'` con este operador.
- En la pregunta 7, `id NOT IN (2,NULL)` no devuelve ids 1 y 3: para ambos hay una comparación desconocida que impide satisfacer el predicado. `NOT EXISTS` y filtros explícitos de NULL pueden expresar la exclusión prevista.
- En PostgreSQL `IS DISTINCT FROM` / `IS NOT DISTINCT FROM` ofrecen comparaciones que tratan NULL de forma explícita, útiles según el requisito concreto.

### Concurrencia de base de datos — prioridad nueva alta

- **Carrera de comprobación/actualización (TOCTOU):** leer `stock` y actualizar más tarde sin coordinación permite que distintas solicitudes observen el mismo inventario antes de descontar.
- **Actualización condicionada y atómica:** una única operación `UPDATE ... WHERE stock>0` en el servidor permite determinar el éxito según las filas actualizadas, evitando sobreventa por esa vía.
- **Write skew:** dos transacciones modifican filas diferentes basándose en una misma condición global y pueden violar una invariante sin conflictos de escritura directos.
- **Aislamiento serializable:** puede impedir estas anomalías, con gestión de abortos y reintentos; también pueden diseñarse mecanismos de bloqueo o restricciones adecuadas al problema.
- **Consistencia de lectura:** las réplicas potencialmente atrasadas no deben utilizarse como verificación definitiva de un inventario reservado en el origen transaccional.

4. **C, Duda, correcta.** SDK de fabricante exclusivo de Windows y USB local, con operación offline, favorece aplicación Windows con integración nativa. Una PWA convencional no puede cargar directamente bibliotecas Windows ni trasladar sin más USB al servidor.
5. **B, Duda, correcta.** Un puente/módulo nativo expone capacidades hardware que el framework compartido no cubre; HTTP no reemplaza la API nativa local y modificar el SO sería desproporcionado.
6. **A, Seguro, correcta.** Ejecutable Windows x86-64 no es directamente compatible con Linux ARM64; recompilar para destino y verificar ABI, dependencias y librerías. Un contenedor por sí solo no transforma la arquitectura o el formato del binario.
7. **C, Seguro, correcta.** El secreto puesto en JS cliente se considera comprometido: rotarlo y guardar el nuevo en un backend. Ofuscación y localStorage siguen exponiéndolo al usuario.
8. **B, Adivinando, correcta.** Un RTOS permite diseñar planificación de tareas críticas según prioridades, plazos y recursos limitados. SO de escritorio/navegador no aportan las garantías adecuadas. **Desconoce RTOS: no consolidado.**

Reforzar ciclo de vida, push, WebSocket, reanudación, permisos y entregas no garantizadas.
10. **B, Adivinando, correcta.** OTA es actualización remota de firmware. La firma digital verifica autenticidad/integridad; particiones A/B conservan firmware funcional y permiten revertir si falla la nueva versión o se interrumpe energía. Sobrescribir firmware activo arriesga inutilizar equipo y quitar verificaciones criptográficas empeora seguridad. **Desconoce OTA y no entendió el escenario: prioridad alta y no consolidado.**
